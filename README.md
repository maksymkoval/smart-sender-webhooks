# Smart Sender — Webhooks (тестове завдання)

Застосунок із входом, списком вебхуків і редагуванням. Стек: React 19 + TypeScript (strict), MSW, TanStack Query, React Router, react-hook-form, Vitest.

## Запуск

Потрібен Node.js 20+.

```bash
npm install
npm run dev        # http://localhost:5173
```

```bash
npm test           # усі тести (Vitest)
npm run typecheck  # tsc --noEmit, strict
npm run build      # typecheck + production build
```

Обов'язковий тест: `src/api/session-refresh.test.ts` → кейс *«two parallel requests with 401 share one rotate…»*.
Запустити лише його: `npx vitest run src/api/session-refresh.test.ts -t "share one rotate"`.

### Тестові облікові дані

| Email | Пароль |
|---|---|
| `demo@smartsender.dev` | `password123` |

Сесія мока діє **30 секунд**. Щоб побачити rotate, зачекайте 30 с і перейдіть на іншу сторінку списку: у DevTools → Network буде `401 → /auth/token/rotate → 200`.

## Структура

```
src/
  api/                    # транспорт і контракт — без React
    http.ts               # CSRF, 419-retry, 401 → rotate → retry (single-flight)
    endpoints.ts          # auth.* і webhooks.* за контрактом
    createApi.ts          # збирає http + endpoints (фабрика, використовується в тестах)
    client.ts             # інстанс для застосунку + подія «сесія завершилась»
    errors.ts, types.ts, fingerprint.ts
  session/                # стан сесії: SessionProvider (login/logout/bootstrap), RequireAuth
  features/
    auth/LoginPage.tsx
    webhooks/             # URL-стан списку, queries, сторінки списку й редагування
  mocks/                  # MSW: backend.ts (чиста логіка «сервера»), handlers.ts (HTTP-шар)
  ui/, lib/               # дрібні UI-примітиви, мапінг серверних помилок у форму
```

Залежності йдуть в одному напрямку: `ui/features → session → api`. Шар `api` нічого не знає про React і роутер, тож його тестую напряму, без рендерингу.

## Ключові рішення

**Сесія та повтори (`src/api/http.ts`).** Вся логіка в одному циклі `request()` із двома незалежними лімітами: не більше одного повтору на 419 і не більше одного на 401.

- *Single-flight rotate.* Модуль тримає `rotation: Promise | null`. Усі запити, що отримали 401 під час ротації, чекають той самий проміс, і rotate виконується один раз.
- *Rotate не запускає rotate.* Auth-ендпоінти передають `skipSessionRefresh`, тому їхній 401 не обробляється перехоплювачем.
- *Застарілий 401.* Клієнт рахує успішні ротації (`sessionEpoch`). Якщо запит відправили до ротації, а 401 прийшов уже після неї, клієнт просто повторює запит, без другого rotate.
- *Фатальні випадки.* Помилка rotate або повторний 401 викликають `onSessionExpired` і кидають `SessionExpiredError`. `SessionProvider` очищає кеш TanStack Query, а `RequireAuth` веде на `/login` і запам'ятовує, звідки прийшов користувач.

**CSRF.** Токен отримується лінивим single-flight запитом `GET /csrf` перед першим API-викликом і кешується. На POST/PUT додається `X-CSRF-TOKEN`. На 419 токен інвалідується (лише якщо його ще не замінив паралельний запит) і запит повторюється один раз. `X-Requested-With: XMLHttpRequest` додається до всіх запитів, а мок його перевіряє.

**Токени.**
- `device_session_token` існує лише як локальна змінна всередині `login()` між `/auth/login` і `/auth/token/issue`. У state, storage чи URL він не потрапляє.
- `fingerprint` — 16 випадкових байтів (`crypto.getRandomValues`) у вигляді 32 hex-символів. Генерується один раз і зберігається в localStorage; якщо storage недоступний, лишається в пам'яті.
- Сесію тримає мок (аналог HttpOnly-cookie). Тому на старті клієнт просто викликає `/v1/me`. З мок-бекендом після перезавантаження це завжди закінчується екраном входу, а з реальним бекендом сесія відновилась би.

**URL — єдине джерело правди для списку.** `useWebhookListParams` читає й пише `page`/`search` через `useSearchParams`, тому перезавантаження та «назад»/«вперед» працюють без додаткового коду.
- Дефолти (`page=1`, порожній пошук) в URL не пишуться.
- Пошук має debounce 300 мс, тож одна завершена фраза дає один запис в історії. Зміна пошуку скидає сторінку.
- Посилання на неіснуючу сторінку (`?page=9`) замінюється на останню реальну.
- Після повторного входу користувач повертається на ту саму адресу з параметрами. Посилання «Back» на формі редагування теж повертає на ту сторінку й пошук, звідки прийшли.

**Серверний стан — TanStack Query.**
- `keepPreviousData` прибирає мерехтіння таблиці при пагінації.
- 4xx і `SessionExpiredError` не повторюються.
- Після збереження деталі оновлюються в кеші, а списки інвалідуються, бо перейменування може змінити результати пошуку.
- Logout і завершення сесії викликають `queryClient.clear()`.

**Форми.** Валідацію виконує сервер. На клієнті лише блокуються порожні поля. Помилки 422 з `error.payload` потрапляють до відповідних полів через `setError` (`lib/serverErrors.ts`), а помилки без відповідного поля показуються над кнопкою. Форма редагування монтується лише після завантаження даних, тому фоновий рефетч не перезапише введений текст.

**Мок.** `MockBackend` — це чистий клас: сесія з TTL, одноразові device-токени, CSRF, валідація, пагінація й пошук. `handlers.ts` лише перекладає HTTP у виклики бекенду й відповідає у форматі помилок контракту. Той самий код працює в браузері (Service Worker) і в тестах (`msw/node`). Він перевіряє заголовок `X-Captcha-Token` (приймає будь-яке непорожнє значення) і CSRF *до* виконання операції. Даних 28 вебхуків у стабільному порядку.

## Тести

- `src/api/session-refresh.test.ts` — тести транспорту на реальних MSW-хендлерах:
  - **обов'язковий:** два паралельні запити отримують 401, rotate виконується рівно один раз (між обома 401 і обома успішними повторами), обидва запити отримують 200. Rotate штучно сповільнено на 50 мс, щоб обидва 401 гарантовано приходили під час ротації.
  - rotate повертає 400, тож сесія завершується і повторного rotate немає;
  - 419, тож CSRF-токен перезапитується й запит повторюється один раз.
- `src/app/App.integration.test.tsx` — наскрізний сценарій справжнього `<App>` у jsdom: deep link, невірний пароль, вхід, обмеження сторінки, пошук, порожній стан, пагінація з «назад»/«вперед», серверна помилка валідації в полі, збереження, прозорий rotate, втрата сесії та повернення на ту ж адресу, вихід.

## Що свідомо не робилося / можна покращити

- **Рантайм-валідація відповідей** (zod тощо). Типи відповідають контракту, але відповіді приводяться через `as T`. Для реального API я б додав схеми на межі `api/`.
- **Мок у production-збірці.** Бекенду немає, тому MSW стартує в усіх режимах. З реальним API це був би лише dev-режим.
- **Капча.** Віджета немає (за умовою), у `endpoints.ts` передається заглушка `X-Captcha-Token`.
- **UI** мінімальний, без бібліотеки компонентів: увага на логіці, а не оформленні.
- **Скасування запитів** при зміні сторінки виконує TanStack Query через `AbortSignal`. На rotate воно навмисно не поширюється, бо ротацію ділять кілька запитів.
